# 由手工物流驱动基础履约状态联动

订单当前值使用六种履约状态：`unknown`（未知）、`pending_shipment`（待发货）、`partially_shipped`（部分发货）、`shipped`（已发货）、`delivered`（已收货）和 `returned`（已退货）。OCR 仍只产生未知、待发货和已发货三种基础识别值。本决策中的手工物流联动只适用于尚无有效发货记录的订单；有发货事实后的履约投影由 ADR 0017 约束。

系统把去除首尾空白后非空的运单号作为唯一有效发货依据；只填快递公司不足以表示已发货。每次单笔或批量保存时，系统先把每笔订单当前值与本次补丁合并，再对合并后的基础状态执行强一致规则：

- `pending_shipment` 且运单号非空时归一为 `shipped`。
- `shipped` 且运单号为空时归一为 `pending_shipment`。
- `unknown`、`delivered` 和 `returned` 不被物流修改静默覆盖。

该归一在补丁合并之后执行，因此即使用户在同一次操作中显式选择了 `pending_shipment` 或 `shipped`，最终值仍必须与运单号是否存在保持一致。显式选择 `unknown`、`delivered` 或 `returned` 则保留用户结论。

联动产生的状态变化与同次物流变化必须在一个数据库事务中保存，只递增一次订单版本，并在同一条人工修改记录中保留实际变化的最小字段集合。它只更新订单当前值，不改写识别原文、来源快照或已冻结的发货快照。

来源快照中的 OCR 识别值仍只接受基础三态；人工确认值可保留已收货或已退货，以如实记录首次入库或来源更新时的人工结论。快照一旦确认仍保持不可变。

这一决策使基础发货状态与可操作的运单依据保持确定性，也避免订单因只填承运商、OCR 误判或物流字段变化而跨越未知、已收货或已退货。代价是系统不验证运单号是否真实发运，也不能从物流轨迹自动得出收货或退货结论；这些情况仍由用户人工核对和修正。

本决策遵守 ADR 0001 的 local-first 边界和 ADR 0002 的派生发货视图边界。手工物流、履约状态、修改记录和事务处理全部保留在用户选择的本机数据目录，不发送给 OCR、候选裁决服务或物流平台，不改变 API Key 的系统凭据库存储方式。
