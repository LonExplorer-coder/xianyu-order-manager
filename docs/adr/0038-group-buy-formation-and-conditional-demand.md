# 团购成团确认与条件性需求的首版规则

规格 12.5 允许团购按三条路径确认成团，但未落定确认触发方式、未成团关闭后的订单去向与成团后的成员边界。工单 #65 实施前由用户拍板，结论如下。

## 决策

1. **成团始终由人工确认**：达到成团数量或到达截止时间只把计划标记为「具备成团条件」并在待办中提示；成团必须由用户点击「确认成团」，确认时选择并记录本次依据（已达成团数量 / 已到截止时间 / 提前成团）。系统不在任何情况下自动成团。
2. **依据在确认时校验**：选「已达数量」要求当时活跃件数 ≥ 成团数量；选「已到截止」要求当前时间 ≥ 截止时间；「提前成团」无前置条件。依据与原因一起记录在不可变的 `formed` 计划事件中。
3. **成团事实用 `formed_at` 列承载**：不新增计划状态值；显示态「团购·已成团待备货」、释放资格都由 `formed_at` 推导。团购计划必须先确认成团才能释放订单。
4. **成团后锁定成员**：确认成团后计划不再接受新订单加入；退出与释放仍允许（买家主动退出、分批释放）。
5. **未成团关闭保留成员**：未成团的团购计划关闭时，成员订单不退出、不恢复发货资格，留在已关闭计划内；计划详情展示「待退款清单」——活跃成员中平台交易状态尚未变为退款或取消的订单。已确认成团的计划关闭仍按现状退出并恢复发货资格。待确认资金事项的正式表结构留给阶段四 #73（其口径决策 #55 未做），本阶段不提前建资金表。
6. **条件性需求复用预售需求投影**：团购计划共享 #64 的需求视图、退款登记与采购建议机制。未成团时需求标注为「条件性团购需求（预测）」，缺口只作预测，不构成确定采购缺口；确认成团后同一数据转为确定需求，转化事实即 `formed` 事件，不搬移数据。
7. **未成团提前采购必须显式确认风险**：未成团计划上创建采购建议时必须勾选「知悉未成团库存风险」，确认时间记入 `purchase_suggestions.risk_acknowledged_at`；缺少确认则拒绝创建。
8. **退款只减对应商品与数量**：发货前退款登记与整单退款/取消收缩钩子扩展到团购成员，语义与预售一致，不覆盖其他参与订单。

## 影响

- 团购「已成团待采购 / 已成团待备货」的细分以需求视图的未覆盖缺口呈现：缺口大于 0 时提示补足采购在途；释放闸门的备货条件由 #66 落地。
- `fulfillment_plan_events.event_type` 的 CHECK 需要加入 `formed`，迁移 v53 以重建表方式完成（先移除不可变触发器再恢复）。
- 规格 16 条规则 12、18（成团前需求只用于预测、提前采购须用户担险）自本 ADR 起有实现承载。
- `formed` 事件的 payload 除依据外快照确认时的活跃件数，使「已达成团数量」依据可复现；成团后仍可修改成团数量等计划条件，历史依据以快照为准。
- 未成团关闭后成员订单的唯一出口是平台交易状态变为退款或取消；若卖家线下退款而平台状态长期不更新，订单会停留在待退款清单。是否提供「线下已退款」人工标记通道，留待 #73 资金事项落地时一并确认。
- 已成团计划关闭、预售计划关闭仍按现状退出成员并恢复发货资格，与未成团关闭不同。
