# 从经过验证的 GitHub Release 半自动更新便携程序

应用只在用户点击“检查更新”后请求项目公开 GitHub 仓库的 latest release，不后台轮询、不静默下载、不自动安装。只有非草稿、非预发布、语义版本高于当前版本，并同时包含当前平台架构的便携 ZIP 与 `portable-<平台>-<架构>.json` 更新证据时，才形成更新候选。下载地址必须是 GitHub HTTPS 地址；更新证据中的版本、平台、架构、ZIP 文件名与 SHA-256 必须全部匹配。

下载写入系统应用配置目录下的更新暂存区，不写入便携程序目录或订单数据目录。用户确认应用前，系统必须使用现有备份引擎创建并验证一个完整可恢复备份；没有可用备份位置时由用户选择。备份未通过、更新 ZIP 未通过 SHA-256 或更新候选发生变化时，不得启动替换。

便携程序在运行中不能可靠覆盖自身，尤其 Windows 会锁定可执行文件。因此当前应用只负责准备更新，随后启动更新辅助程序并退出。辅助程序先解压候选，在隔离目录使用已验证备份恢复数据副本并运行候选健康检查；通过后等待当前进程退出，把旧程序目录移动到同级回滚目录，再把候选移动到原路径。任一步失败都恢复旧程序目录；成功后启动新程序并清理回滚目录。订单数据目录始终位于程序目录之外，不参与移动或重写。

## 硬约束

### PU-01 完全由用户触发
- 检查、下载和应用分别由用户显式触发；应用不得后台强制更新。

### PU-02 发布证据绑定
- 更新 ZIP 必须与同一正式发布中的便携验收证据逐项匹配，并在下载后复算 SHA-256。

### PU-03 备份先于替换
- 只有现有备份引擎创建并验证成功后才能启动更新辅助程序；备份失败不得触碰当前程序目录。

### PU-04 候选先行健康检查
- 更新候选必须在替换前针对已验证备份的隔离恢复副本完成启动与数据库升级检查；不得先用真实订单数据目录试错。

### PU-05 旧程序可回滚
- 替换时先保留旧程序目录；候选移动失败必须恢复旧目录，新程序启动前不得删除旧目录。

### PU-06 数据目录隔离
- 更新下载、解压、程序替换与回滚不得移动、覆盖或重写独立订单数据目录。
