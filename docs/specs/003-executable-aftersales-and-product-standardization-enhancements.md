# 可执行售后流程与商品标准化增强方案

- 状态：方案已确认，尚未实施
- 日期：2026-08-15
- 适用范围：售后流程模板、已有订单商品标准化、商品映射管理、标准商品默认订单单价
- 不包含：任意脚本工作流、自动改写历史订单、库存和财务模块的实际记账

## 1. 为什么需要这次增强

当前有两个已经确认的产品缺口，以及一个在讨论中补充确认的关联需求。

第一，自定义售后流程目前只是版本化流程向导。界面可以按照用户配置的步骤和顺序展示，但真正出现什么按钮、允许执行什么动作，仍由固定售后状态判断。用户看到的是自定义流程，实际操作却没有按该流程推进，容易误以为配置没有生效。

第二，标准商品和商品映射已经存在，但已有订单只能在截图识别或订单更新校对时关联标准商品。普通订单详情、订单商品明细和标准商品页面缺少直接入口；映射规则本身也没有可视管理列表，用户不知道一个 SKU 已经积累了多少原文映射、关联订单和商品数量。

第三，人工给订单新增商品时，已经维护好的标准商品名称、规格和常用单价不能直接带入，导致用户仍要重复输入。

本方案把三个问题放在同一条完整操作链中解决：

1. 自定义售后流程从“只显示”升级为“受约束地执行”；
2. 已有订单可以单笔或批量关联标准商品；
3. 商品映射变得可查看、可修正、可追溯；
4. 标准商品可以保存一个录入用的默认订单单价；
5. 选择标准商品时可以一次性带入名称、规格和单价，但不能静默改写来源证据或历史金额。

## 2. 总体原则

### 2.1 流程不能制造事实

流程模板决定正常业务操作的顺序和允许入口，但不能伪造退货收到、商品检查、实际退款、补发或物流异常。真实事实仍由各自的业务记录保存。

### 2.2 事实可以满足流程

已经存在的真实事实可以自动满足流程步骤。例如已有足额实际退款时，“确认退款”步骤直接显示已完成，不要求再次退款；部分退款只显示部分完成和剩余金额。

### 2.3 来源原文与标准商品分开保存

截图或历史导入得到的原始商品标题、原始规格和订单单价属于订单来源证据。标准商品是内部规范身份。关联标准商品不能覆盖来源原文。

### 2.4 映射规则与历史关联分开管理

商品映射决定以后遇到相同原文时如何自动匹配；订单商品上的标准商品关联是已经确认的业务结果。修改映射默认只影响未来，历史订单必须通过单独预览和确认才能批量更正。

### 2.5 目录价格只是录入默认值

标准商品默认订单单价只用于减少人工录入，不代表实际成交价、采购成本或平台结算价，也不能自动修改成交金额。

## 3. 方案一：受约束的可执行售后流程

### 3.1 固定基础场景

系统继续保留以下基础场景：

1. 仅退款；
2. 退货退款；
3. 换货；
4. 直接补发；
5. 拦截退回；
6. 丢件处理；
7. 其他处理。

用户不能直接创造系统完全不认识的底层业务场景，但可以基于一个基础场景创建多个可执行流程版本。例如“退货退款”可以拥有常规版、高价值商品先检查版、老客户先退款版和低价值免退版。

### 3.2 流程步骤必须绑定已有业务动作

每个可执行步骤只能绑定系统已经定义的领域动作，例如：

- 记录协商结果；
- 登记买家退货物流；
- 确认实际收到退货；
- 检查退回商品；
- 确认实际退款；
- 建立补发轮次；
- 创建承运索赔；
- 完成售后。

模板可以改变顺序、必需性、字段要求和简单显示条件，但不能添加任意脚本、循环或自由代码。

### 3.3 两类流程步骤

#### 事实型步骤

事实型步骤必须由真实业务事实满足，不能被人工点击“完成”。典型步骤包括：

- 确认实际收到退货；
- 检查退回商品；
- 确认实际退款；
- 确认补发包裹已经实际发出。

如果步骤因现实变化不再适用，例如退货包裹确认丢失，系统应显示“不再适用”并给出原因，而不是允许用户伪造“已经收到”。

#### 管理型步骤

管理型步骤保存人与业务之间的处理确认，例如：

- 与买家确认诉求；
- 核对退款金额；
- 上传沟通凭证；
- 填写处理备注。

管理型步骤可以带原因跳过，但必须保存跳过原因、操作时间、采用的流程版本和剩余风险。

### 3.4 步骤状态

每个步骤至少存在以下可见状态：

- 未开始；
- 当前待办；
- 部分完成；
- 已完成；
- 已跳过；
- 不再适用。

步骤状态由流程定义和真实事实共同计算。系统不能只保存一个“步骤完成”布尔值来代替退款、退货、检查或补发事实。

### 3.5 正常操作受流程约束，真实事实始终允许补录

正常业务动作按照流程顺序开放。有事实依赖的动作必须严格阻止，例如没有实际收到退货时不能检查商品。

但是，现实中已经发生的事情不能因为流程还没走到那里而无法登记。例如买家提前寄回、商家先行退款或承运方提前赔付，都可以补录真实事实。补录后：

- 对应后续步骤自动显示完成或部分完成；
- 前面尚未完成的管理步骤继续保留；
- 后续事实不能反向伪造前置事实；
- 当前待办按剩余未满足步骤重新计算。

### 3.6 退款步骤的判断

“确认退款”按照真实资金记录判断：

| 已有事实 | 流程结果 |
| --- | --- |
| 只有退款申请 | 未完成，等待确认实际退款 |
| 足额实际退款 | 已完成 |
| 部分实际退款 | 部分完成，显示已退与剩余金额 |
| 退款申请取消且没有实际退款 | 未完成 |
| 退款发生在采用当前流程之前 | 仍视为已完成，保留原发生时间 |
| 实退金额超过当前目标 | 金额冲突，要求人工核对 |

部分退款后允许用户补退剩余金额、调整目标金额或带原因结束退款，系统不能直接把整个步骤视为完成。

### 3.7 进行中切换流程版本

只有进行中的售后可以切换流程版本。切换必须选择新版本并填写原因。

切换后不从第一步重新开始，而是使用已有事实重新计算新版本：

- 已有事实满足的步骤直接完成；
- 部分满足的步骤显示部分完成；
- 尚未满足的步骤成为当前待办；
- 新版本删除的提示步骤不再显示，但对应事实仍保留；
- 已完成或已取消售后不能切换版本。

### 3.8 界面呈现

售后面板应优先显示：

1. 当前流程名称和版本；
2. 当前唯一主步骤；
3. 当前允许执行的主要操作；
4. 部分完成金额或数量；
5. 其余步骤概览；
6. 流程切换与带原因跳过入口；
7. 折叠的流程版本和步骤历史。

流程动作被事实阻止时，界面必须解释原因，而不是只隐藏按钮。

### 3.9 一次性升级现有模板

现有系统预置和自定义模板通过一次性数据升级绑定到已定义的业务动作。无法可靠绑定的自定义步骤标记为“需要检查”，在用户确认之前仍可查看但不能作为可执行步骤。升级完成后不保留“旧向导模式”与“可执行模式”两套长期分支。

## 4. 方案二：已有订单直接关联标准商品与 SKU

### 4.1 三个操作入口

#### 订单详情：单笔关联

每个订单商品提供“关联标准商品”入口，显示来源原文、当前关联、候选标准商品、关联来源和显示偏好。

#### 订单商品明细：批量关联

用户可以筛选相同或相似的标题和规格，选择多条订单商品，统一关联到一个 SKU。确认前必须显示影响订单、商品条目、商品数量、已发货订单和存在售后订单的数量。

#### 标准商品页面：反向查找

标准商品详情后续提供以下列表：

- 已关联订单商品；
- 完全一致但尚未关联的商品；
- 可由已有映射关联的商品；
- 只具有相似文字的人工候选；
- 无法判断的未关联商品。

第一实施切片先完成单笔关联与批量关联，反向查找作为下一切片，但三者使用同一关联规则。

### 4.2 商品映射可视列表

标准商品详情增加“商品映射”区域，并区分以下统计：

- 当前有效映射规则数；
- 已关联订单数；
- 已关联订单商品明细数；
- 已关联商品总数量。

每条映射显示：

- 原始商品标题；
- 原始规格；
- 规范化后的匹配值；
- 目标 SKU 和标准商品；
- 适用范围；
- 建立来源；
- 建立时间；
- 最近使用时间；
- 命中订单数。

用户可以搜索、新增、更正、停用或删除映射，并能从映射进入关联订单。删除和更正保留历史。

### 4.3 映射适用范围

标准商品和 SKU 在整个本机工作区共用。商品映射具有三级适用范围：

1. 当前平台与当前卖家账号；
2. 当前平台的全部账号；
3. 整个工作区。

新建映射默认采用最安全的“当前平台与当前卖家账号”。匹配优先级为：

```text
当前账号映射
→ 当前平台映射
→ 工作区映射
→ 唯一的标题规格完全一致
→ 只展示模糊候选
```

界面必须说明最终命中了哪一级规则。

### 4.4 映射唯一性与单笔例外

在同一个映射适用范围内，同一组规范化后的“原始标题＋原始规格”只能指向一个当前有效 SKU。

发生冲突时，用户可以：

1. 取消；
2. 更正当前映射目标；
3. 只把本次订单商品关联到另一个 SKU，不修改映射。

单笔例外关联不能污染未来自动匹配。

### 4.5 映射变更不自动改写历史订单

新增、更正、停用或删除映射默认只影响以后进入识别、校对或人工关联的商品。系统可以查找历史候选，但必须经过单独预览和确认才能批量重新关联。

批量更正前至少显示：

- 原关联与新关联；
- 影响订单数；
- 影响商品明细数；
- 商品总数量；
- 已发货订单数；
- 存在售后订单数；
- 是否涉及未来库存和财务归类调整。

### 4.6 任何阶段都允许商品身份更正

订单未发货、已发货、已退款或存在售后时，都允许更正标准商品关联，但更正只改变商品身份归属：

- 来源标题、来源规格、数量不变；
- 发货、退货、退款、补发和索赔事实不变；
- 保存更正前后 SKU、原因、时间和影响范围；
- 当前订单查询、统计和导出使用新关联；
- 将来若已有库存或财务流水，则通过独立的 SKU 归类更正记录调整归属，不静默改写原流水。

### 4.7 标准商品显示偏好

关联时提供并默认勾选“优先展示标准商品信息”。

勾选后，订单列表、订单详情主标题、发货组、售后和普通导出商品列优先显示标准商品名、标准规格和 SKU。取消后，这些位置优先显示订单来源标题和来源规格。

明确命名为“原始商品标题”“原始规格”“标准商品名”“标准规格”“SKU”的字段始终输出自己的真实值，不受显示偏好影响。显示偏好可以单独修改，不需要解除关联。

## 5. 方案三：标准商品默认订单单价与一次性带入

### 5.1 默认订单单价

标准商品新增一个可选的“默认订单单价”。第一版每个 SKU 只保存一个当前默认值，同时以不可变价格变更记录保存前后价格、原因和时间。

默认订单单价：

- 只用于人工录入预填；
- 可以为空；
- 使用整数分或等价的精确金额语义；
- 不代表实际成交金额；
- 不代表采购成本；
- 不代表平台结算价格；
- 修改后不回写任何历史订单。

第一版不提供按平台、账号、客户或日期配置多套价格表。

### 5.2 一次性带入，不持续联动

用户选择标准商品时，可以一次性带入当时的名称、规格和默认订单单价。以后修改标准商品，不自动修改已经录入的订单。

#### 人工新增订单商品

选择 SKU 后默认：

- 勾选带入标准商品名；
- 勾选带入标准规格；
- 标准商品有默认订单单价时，勾选带入单价；
- 数量默认仍为 1，用户可以修改。

#### OCR 或历史订单商品

选择 SKU 后默认只建立关联并优先展示标准商品信息：

- 不覆盖来源标题；
- 不覆盖来源规格；
- 不覆盖 OCR 或历史单价；
- 如需使用标准商品默认单价，必须额外勾选并确认金额变化。

### 5.3 金额计算与提示

带入或修改商品单价后：

1. 商品小计自动按“单价 × 数量”计算；
2. 系统计算新的商品明细合计；
3. 系统明确提示是否同步更新商品总价；
4. 成交金额永远不自动修改；
5. 运费不自动修改。

提示至少包含：

```text
商品单价：原值 → 新值
商品小计：原值 → 新值
商品总价：原值 → 建议值
成交金额：保持不变
```

如果商品明细合计与成交金额存在差异，系统只提示可能存在优惠、议价或其他原因，不自动把两者改成一致。

## 6. 批量操作的安全默认值

批量关联已有订单商品时，默认选项为：

```text
☑ 关联到所选 SKU
☑ 优先展示标准商品信息
☐ 使用标准商品默认单价
☐ 建立未来自动匹配的商品映射
```

确认前必须显示：

- 订单数量；
- 商品明细数量；
- 商品总数量；
- 未关联、关联相同 SKU、关联其他 SKU 的数量；
- 已发货和存在售后的订单数量；
- 是否修改商品单价；
- 是否建议修改商品总价；
- 成交金额保持不变；
- 来源原文保持不变；
- 是否新增或更正商品映射。

以下冲突不能静默通过：

- 商品已经关联其他 SKU；
- 标准商品没有默认单价却要求同步价格；
- 相同原文已有指向其他 SKU 的有效映射；
- 订单正在被其他操作修改；
- 商品总价与成交金额出现需要人工核对的明显差异。

## 7. 数据与审计边界

目标数据至少包括：

- 可执行售后流程模板版本；
- 流程步骤绑定的已有业务动作；
- 管理型步骤完成或跳过事件；
- 售后流程版本切换事件；
- 标准商品默认订单单价；
- 默认订单单价变更历史；
- 商品映射适用范围和当前有效状态；
- 商品映射建立、更正、停用和删除历史；
- 订单商品标准化关联；
- 标准商品显示偏好；
- 商品身份更正历史；
- 批量关联操作及其逐条结果。

事实型流程步骤不另存一份假的完成事实；它们始终从退款、退货、检查、发货和索赔等现有事实投影。

## 8. 推荐实施顺序

### 第一切片：补齐可达入口

- 订单详情单笔关联标准商品；
- 订单商品明细批量关联；
- 标准商品默认订单单价；
- 人工新增商品时一次性带入；
- 明确的金额变化提示。

### 第二切片：映射管理

- 标准商品的商品映射列表；
- 映射统计、搜索、范围和冲突处理；
- 历史候选预览与批量重新关联；
- 商品身份更正审计。

### 第三切片：可执行售后流程

- 步骤绑定已有业务动作；
- 事实型和管理型步骤；
- 流程约束、事实满足和部分完成；
- 带原因跳过和不再适用；
- 进行中切换版本；
- 一次性升级已有流程模板。

这个顺序先解决已有订单与 SKU 关联的明显入口缺失，再补齐映射管理，最后替换售后流程执行边界。三个切片都可以独立验收。

## 9. 验收清单

### 9.1 可执行售后流程

- 自定义调整步骤顺序后，正常业务按钮按照新顺序开放；
- 没有实际收到退货时不能检查；
- 已有足额退款自动满足退款步骤，不重复退款；
- 部分退款显示已退金额与剩余金额；
- 提前发生的真实退货、退款或赔付可以补录；
- 事实型步骤不能人工伪完成；
- 管理型步骤带原因跳过并可追溯；
- 切换流程版本后已有事实不丢失，新步骤状态重新计算；
- 已完成或已取消售后不能切换版本；
- 模板不能创建任意脚本或系统未定义的业务动作。

### 9.2 已有订单与商品映射

- 普通订单详情可以直接关联标准商品；
- 订单商品明细可以批量关联；
- 标准商品可以看到映射规则数、订单数、商品明细数和商品总数量；
- 映射列表可以查看范围、来源、时间、命中量和关联订单；
- 同范围同原文不能同时指向两个 SKU；
- 单笔订单可以作为例外关联而不修改映射；
- 修改映射不自动重写历史订单；
- 历史订单批量更正必须先预览；
- 已发货和售后订单的 SKU 可以带原因更正，但业务事实不变；
- 显示偏好默认选择标准商品信息，来源原文始终可查。

### 9.3 默认订单单价

- 标准商品可以保存空值或一个当前默认订单单价；
- 价格变更有前后值和时间；
- 人工新增商品可以一次性带入名称、规格和单价；
- OCR 或历史商品关联时默认不覆盖来源值和单价；
- 用户显式同步单价前可以预览变化；
- 商品小计自动重算；
- 商品总价只在用户确认后更新；
- 成交金额和运费不自动修改；
- 后续修改标准商品默认单价不影响历史订单。

## 10. 明确不做

- 不开放任意脚本、循环或自由代码工作流；
- 不让流程模板绕过退款、退货、检查、补发和物流异常的领域校验；
- 不允许人工把不存在的退款或退货事实标记为完成；
- 不因新增或修改映射静默批量改写历史订单；
- 不覆盖截图原始商品标题和原始规格；
- 不把默认订单单价当成实际成交金额或采购成本；
- 不在本方案中实现平台、客户或日期维度的复杂价格表；
- 不在本方案中实现库存和财务流水，只保留以后进行 SKU 归类更正的边界。
