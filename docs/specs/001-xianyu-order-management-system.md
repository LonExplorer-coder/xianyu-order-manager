# 闲鱼订单管理系统产品规格

- 状态：已确认，实施中
- 日期：2026-07-27
- 产品范围：个人内部使用的本机订单管理应用
- 当前平台：闲鱼
- 主验收边界：完整订单工作流
- GitHub Issue：https://github.com/LonExplorer-coder/xianyu-order-manager/issues/1

## Problem Statement

个人卖家收到闲鱼订单后，需要从订单详情截图中反复抄录订单编号、收件信息、商品、金额和时间等内容，再手工整理到不同用途的表格。这个过程耗时、容易抄错，也难以处理一个买家连续下多笔订单、多商品订单、重复截图和订单状态变化。

固定表头无法适应订单总览、发货、财务和分享等不同场景；直接压缩多笔订单又会丢失原订单号、付款与退款记录。截图还包含姓名、手机号和地址，系统需要在提供高质量云端识别的同时，把长期数据控制在用户自己的电脑上。

## Solution

提供一个 macOS 与 Windows 均可免安装运行的本机网页应用。用户批量上传完整的闲鱼订单详情截图，系统通过用户自己的阿里云百炼 qwen3.5-ocr 服务生成识别原文，再由本机规则拆分字段、执行确定性校验和重复检测，将结果自动入库或送入校对页。

系统始终保留每笔原始订单及商品明细，并针对相同手机号和完整地址的未发货订单生成合并发货组。用户可维护标准商品与 SKU 映射、创建多套表格模板、导入历史 Excel，并导出订单总表、商品明细表和合并发货表。订单数据、截图和备份保存在本机；导出默认脱敏，系统界面显示完整信息。

## User Stories

### 启动与访问

1. 作为个人卖家，我希望在 macOS 上解压后直接启动应用，以便不安装开发环境或使用命令。
2. 作为个人卖家，我希望在 Windows 上解压后直接启动应用，以便在两种桌面系统上使用同一产品。
3. 作为个人卖家，我希望首次启动时选择独立的数据目录，以便替换或删除程序文件时不丢失订单。
4. 作为个人卖家，我希望桌面端默认不要求启动密码，以便个人日常使用保持直接。
5. 作为个人卖家，我希望没有订单时首页突出上传入口，以便首次使用时立即知道下一步。
6. 作为个人卖家，我希望已有订单时首页以订单表为主，并显示批量上传入口、待确认数、待发货数和最近批次，以便快速进入日常工作。
7. 作为个人卖家，我希望从同一 Wi-Fi 的手机扫码打开上传页，以便不先把手机截图传到电脑。
8. 作为个人卖家，我希望手机上传入口使用临时访问码且默认关闭，以便局域网中的其他设备不能随意访问订单。

### 截图上传与批次

9. 作为个人卖家，我希望一次上传多张普通截图或长截图，以便批量处理订单。
10. 作为个人卖家，我希望每个识别批次最多包含 50 张截图，以便系统负载和失败范围可控。
11. 作为个人卖家，我希望可以连续创建多个识别批次，以便订单量超过 50 张时分批处理。
12. 作为个人卖家，我希望一张来源截图只对应一个完整订单，以便识别边界明确。
13. 作为个人卖家，我希望系统检查截图是否包含完整收件信息、全部商品和订单编号区域，以便截断的截图不会静默入错。
14. 作为个人卖家，我希望看到每张截图和整个批次的排队、识别、校验、待确认、成功和失败进度，以便知道处理状态。
15. 作为个人卖家，我希望离开上传页面后批次仍能在应用运行期间继续处理，以便不必一直停留在进度页。
16. 作为个人卖家，我希望断网或云服务不可用时截图先保存在本机并进入等待识别状态，以便恢复网络后继续而不丢批次。
17. 作为个人卖家，我希望可以手动重试失败任务或改为人工录入，以便外部服务故障不阻断工作。
18. 作为个人卖家，我希望来源截图默认与订单关联保留，以便以后核对识别结果。

### OCR 配置与识别

19. 作为个人卖家，我希望在设置页分别配置百炼 OCR 与可选的 OpenAI 兼容候选裁决服务，并分别测试连接，以便 OCR 和 DeepSeek、百炼或自定义文本模型可以使用独立凭据。
20. 作为个人卖家，我希望本机截图直接以受支持的图片数据形式发送给 OCR，而不是先公开上传到图床，以便减少额外暴露。
21. 作为个人卖家，我希望系统从闲鱼订单详情页提取订单、买家、商品、金额和时间字段，以便免去手工抄录。
22. 作为个人卖家，我希望一个订单可以识别多个商品明细，以便处理多商品订单。
23. 作为个人卖家，我希望截图未显示商品数量时默认数量为 1，以便商品汇总仍有明确数量。
24. 作为个人卖家，我希望可以开启或关闭自动入库，以便在效率和谨慎之间切换。
25. 作为个人卖家，我希望关闭自动入库时所有识别结果先进入校对页，以便确认后再写入正式订单表。
26. 作为个人卖家，我希望开启自动入库后，只有关键字段完整、格式有效且无重复冲突的订单才自动保存，以便避免静默错误。
27. 作为个人卖家，我希望订单编号、收件人、手机号、完整地址、至少一项商品和成交金额任一缺失时进入待确认，以便关键业务数据不残缺。
28. 作为个人卖家，我希望系统用完整图生成识别原文，在本机划分六个订单语义区域、隔离推广内容并确定性拆分字段，以便 OCR 模型只负责识别而不负责推断业务结论。
29. 作为个人卖家，我希望定位缺失或关键字段没有识别原文依据时必须人工确认；规则只能得到多个有限候选时，可以选择启用独立模型裁决，以便系统不把自由生成内容当成事实。
30. 作为个人卖家，我希望系统用格式、完整性和交叉一致性规则标记可疑字段，并能追溯候选裁决采用、拒绝或无法确定的依据，而不是展示没有依据的模型置信度。
31. 作为个人卖家，我希望看到本月识别张数、成功率和估算费用，以便掌握云端使用成本。
32. 作为个人卖家，我希望设置月度额度并选择只提醒或暂停识别，以便费用超出预期时仍由我决定。

### 原始订单与校对

33. 作为个人卖家，我希望每个订单保存平台、卖家账号、订单编号、支付宝交易号、平台交易状态和履约状态，以便完整追溯交易与发货。
34. 作为个人卖家，我希望每个订单保存下单时间、付款时间、商品总价、运费和成交金额，以便查询和统计。
35. 作为个人卖家，我希望保存买家昵称、收件人、手机号、完整地址以及省市区拆分，以便发货和筛选。
36. 作为个人卖家，我希望商品明细保存原始标题、原始规格、单价、数量、小计、标准商品名、标准规格和 SKU，以便同时保留来源和标准化结果。
36A. 作为个人卖家，我希望订单总表把每个商品条目动态展开为相邻的商品、款式或规格和数量列，以便不打开商品明细也能直接查看并操作一笔订单中的全部商品。
36B. 作为个人卖家，我希望商品明细明确区分原始商品标题、原始款式或规格和数量来源，以便识别原文、系统推定值与未来标准商品不会混淆。
36C. 作为个人卖家，我希望数量同时存在人工修改、OCR 识别和系统默认值时优先采用人工修改，其次采用 OCR 识别，最后才采用系统默认 1，以便后续识别不会静默覆盖人工确认结果。
37. 作为个人卖家，我希望保存导入时间、来源截图、识别状态、合并组、快递公司、运单号和备注，以便管理完整生命周期。
38. 作为个人卖家，我希望在校对页直接修改字段并查看来源截图，以便快速纠正识别错误。
38A. 作为个人卖家，我希望在订单入库后仍可从订单详情编辑当前字段和商品明细，并在保存前看到变化，以便纠正后来发现的错误而不删除重建订单。
39. 作为个人卖家，我希望系统记录字段修改前后内容、时间和修改来源，以便追查识别和人工修改。
40. 作为个人卖家，我希望内容完全相同的重复订单自动跳过，以便同一截图不会重复入库。
41. 作为个人卖家，我希望同一订单编号的新截图内容发生变化时查看新旧字段对比，并保留新的来源快照，以便确认是否更新。
42. 作为个人卖家，我希望系统绝不静默覆盖已有订单，并保留更新记录与来源快照，以便交易历史可追溯。
43. 作为个人卖家，我希望分别管理平台交易状态、履约状态和识别状态，并在履约状态中区分未知、待发货、已发货、已收货和已退货，以便待确认、交易取消或退款不会与发货进度混为一个含义。
44. 作为个人卖家，我希望批量修改履约状态、快递公司和运单号，以便高效处理发货。
44A. 作为个人卖家，我希望待发货订单填入运单号时自动变为已发货，而已发货订单清空运单号时自动退回待发货，以便基础履约状态与有效发货依据保持一致。
44B. 作为个人卖家，我希望已收货和已退货由我明确维护，而不是被 OCR 或物流字段静默推断，以便终态符合真实处理结果。
45. 作为个人卖家，我希望取消或退款订单仍被保留，但默认不进入待发货和合并汇总，以便历史完整且发货清单正确。
46. 作为个人卖家，我希望按日期、状态、平台账号、买家、商品和是否合并进行搜索、筛选和排序，以便快速找到目标订单。

### 合并发货

47. 作为个人卖家，我希望系统优先用规范化手机号提示可能来自同一买家的订单，以便发现可合并的多笔订单。
48. 作为个人卖家，我希望手机号缺失时系统只提示姓名和地址相似，而不自动认定同一买家，以便避免同名误合并。
49. 作为个人卖家，我希望只有手机号和完整地址都一致的未发货订单才自动进入同一合并发货组，以便不同地址不会错发。
50. 作为个人卖家，我希望同一手机号但地址不同的订单显示为同一买家下的不同发货组，以便保留买家关系但分开发货。
51. 作为个人卖家，我希望原始订单始终保留并可从合并发货组追溯，以便不丢失订单号和付款记录。
52. 作为个人卖家，我希望合并发货表汇总收件信息、成员订单、商品、数量、金额和订单数量，以便一次完成拣货与发货。
53. 作为个人卖家，我希望可以手动拆分或重新组合发货组，以便处理系统规则无法判断的特殊情况。
54. 作为个人卖家，我希望跨不同地址手动合并时必须明确选择最终收货信息，以便发货单不会使用含糊地址。
55. 作为个人卖家，我希望未发货的合并发货组随原始订单修改、取消或退款实时更新，以便发货前看到最新结果。
56. 作为个人卖家，我希望合并发货组标记已发货时冻结发货快照，以便历史包裹内容不被之后的修改改变。
57. 作为个人卖家，我希望已发货后原始订单变化只产生警告而不自动改写快照，以便异常由我决定如何处理。
58. 作为个人卖家，我希望同一买家的后续新订单创建新的未发货组，以便不会混入已经发出的历史包裹。

### 商品标准化

59. 作为个人卖家，我希望同时保留截图原始商品文字和标准商品信息，以便既可核对来源又可准确统计。
60. 作为个人卖家，我希望维护 SKU、标准商品名、标准规格和标题别名，以便同一商品的不同写法汇总到一起。
61. 作为个人卖家，我希望完全一致或已有映射的标题自动归并，以便减少重复校对。
62. 作为个人卖家，我希望相似标题只提供候选而不静默归并，以便模糊匹配不会造成拣货错误。
63. 作为个人卖家，我希望在校对订单时创建或确认商品映射，以便校对结果服务于后续订单。
64. 作为个人卖家，我希望批量导入和导出商品目录 Excel，以便复用已有 SKU 数据。
65. 作为个人卖家，我希望重复修正同类字段时系统在本机提示建立映射，而不自动改历史订单，以便学习过程保持可控。

### 字段库、表格模板与导入导出

66. 作为个人卖家，我希望从内置字段库中选择列、改名和排序，以便表格符合自己的工作习惯。
67. 作为个人卖家，我希望新增文本、数字或金额、日期时间、单选、多选和勾选字段，并明确它适用的表格数据粒度，以便记录平台截图之外的业务信息。
68. 作为个人卖家，我希望给自定义字段设置默认值和是否必填，以便批量录入保持一致。
69. 作为个人卖家，我希望自定义字段可以参与筛选和排序，以便它们不是仅用于展示的备注。
70. 作为个人卖家，我希望保存多套命名表格模板，并明确每套模板面向订单、商品明细或发货组，以便不同粒度不会混用列定义。
71. 作为个人卖家，我希望表格模板同时保存字段、改名、顺序、筛选和排序，以便打开模板时立即恢复工作视图。
72. 作为个人卖家，我希望系统提供商品总数量、订单总额、合并订单数和合并总额等内置计算字段，以便常见统计无需公式。
73. 作为个人卖家，我希望应用内不开放任意公式，以便错误公式不会污染订单数据。
74. 作为个人卖家，我希望导入已有历史订单 Excel，并在入库前映射表头、预览结果和错误行，以便迁移现有数据。
75. 作为个人卖家，我希望从发货组导出的同一个 Excel 文件包含订单总表、订单商品明细表和合并发货表，以便兼顾订单、商品和发货三个粒度。
76. 作为个人卖家，我希望第二阶段起为三个工作表分别应用对应粒度的表格模板，以便列定义与每行代表的对象一致。
76A. 作为个人卖家，我希望订单模板中的动态商品列组可以分别修改商品、款式或规格和数量的基础表头，并由系统按当前结果自动编号完整展开，以便兼顾自定义表头与多商品订单。
77. 作为个人卖家，我希望导出默认对指定个人信息脱敏，以便分享文件时降低隐私风险。
78. 作为个人卖家，我希望每次导出都可以明确选择保持默认脱敏或临时关闭脱敏，以便内部发货可以使用完整信息，对外分享时继续保护隐私。
79. 作为个人卖家，我希望默认将收件人保留姓氏、手机号保留前 3 后 4 位、地址保留省市区并遮盖街道门牌、昵称保留首尾字符，以便无需配置也有合理保护。
80. 作为个人卖家，我希望系统界面显示完整收件信息，仅导出时执行脱敏，以便内部操作不受遮挡影响。

### 数据生命周期与可靠性

81. 作为个人卖家，我希望来源截图超过 90 天后自动转为高质量压缩图，以便控制磁盘占用。
82. 作为个人卖家，我希望截图默认永不自动删除，并可选择在 180 天或 365 天后清理，以便在容量和核对能力之间选择。
83. 作为个人卖家，我希望删除截图前看到预计释放空间并二次确认，以便避免意外丢失核对依据。
84. 作为个人卖家，我希望删除来源截图不影响已提取订单数据，以便清理存储后仍能工作。
85. 作为个人卖家，我希望删除订单先进入回收站并保留 30 天，以便误删后可恢复订单、商品、合并关系和截图。
86. 作为个人卖家，我希望每天自动创建一次增量去重备份并保留最近 30 个版本，以便本机故障后可恢复。
87. 作为个人卖家，我希望备份包含订单、模板、商品映射和截图，并可选择外接硬盘或同步盘目录，以便备份完整且位置可控。
88. 作为个人卖家，我希望备份默认上限为 5 GB 且可以修改，以便容量不会无限膨胀。
89. 作为个人卖家，我希望超过备份上限时清理最旧版本但始终保留最近一次完整可恢复备份，以便容量受控且不会失去恢复点。
90. 作为个人卖家，我希望一键创建备份、验证备份并恢复数据，以便迁移或故障恢复不依赖手工复制内部文件。
91. 作为个人卖家，我希望通过备份文件在 Mac 和 Windows 之间迁移数据，以便无需云端实时同步也能换设备。
92. 作为个人卖家，我希望更新便携版程序时先自动备份数据，以便更新失败仍可继续使用旧版本。
93. 作为个人卖家，我希望由自己确认后下载和应用更新，而不是后台强制升级，以便工作流程不被突然打断。
94. 作为个人卖家，我希望应用界面简洁、清晰、直观、专注且偏商务，以便长时间处理表格时保持效率。

## Implementation Decisions

### 产品边界与运行形态

1. 产品是个人内部工具，不提供注册、团队成员、角色权限、订阅或计费。
2. 产品以本机优先方式运行，交付 macOS 与 Windows 免安装便携版。程序与数据目录分离，默认数据目录位于系统文档目录下，并允许首次启动时选择。
3. 桌面端不要求启动密码。手机局域网上传模式默认关闭，开启后使用二维码和临时访问码。
4. Mac 与 Windows 之间不做实时同步；跨设备迁移通过备份与恢复完成，同一数据目录同一时刻只允许一个应用实例写入。活动数据库不直接放在同步盘供多台设备打开，外接硬盘或同步盘只作为备份目标。
5. 第一版只支持 iOS 或 Android 上的闲鱼订单详情页普通截图或长截图。数据模型保留平台和卖家账号维度，但不实现其他平台识别；每个识别批次必须关联来源平台与卖家账号，当前唯一账号作为默认值。

### 最高层模块边界

6. 应用围绕一个完整订单工作流组织：截图接收、OCR 适配、结构化规范化、业务校验、人工校对或自动入库、原始订单持久化、合并发货投影、表格呈现和导出。
7. OCR 服务通过可替换适配器隔离。业务层只接收统一的识别结果和错误，不依赖阿里云原始响应形状。
8. 合并发货表是由原始订单生成的派生投影；发货快照是独立的历史事实，不由之后的动态投影覆盖。
9. 表格模板和导出层只读取字段库与查询结果，不拥有订单事实。自定义列值与内置字段分开管理。
10. 图片生命周期、备份和恢复属于本机存储边界，不与订单识别逻辑混合。

### 本机存储与核心数据

11. 使用事务型嵌入式关系数据库保存结构化数据，使用文件系统保存来源截图、压缩图和备份；两者都位于用户选择的数据目录。
12. 核心记录至少包括平台、卖家账号、识别批次、来源截图、来源快照、识别尝试、订单草稿、待确认项、原始订单、商品明细、合并发货组、发货快照、标准商品、商品映射、字段定义、表格模板、审计记录和备份记录。
13. 原始订单以平台、卖家账号和订单编号形成业务唯一性约束。一个原始订单可以关联多个不可变来源快照；订单当前值可以校对和更新，但不能覆盖来源证据。来源截图同时保留内容指纹，用于检测完全重复图片。
14. 地址同时保存截图原文、规范化完整地址及省市区拆分。任何规范化结果都不能覆盖原文。
15. 金额以整数分或精确十进制语义保存，禁止二进制浮点；成交金额用于交叉校验但不强制等于商品总价加运费，因为平台优惠可能造成差异。订单号、交易号和手机号按字符串保存与导出。时间按原始文本与规范化时间共同保存，默认业务时区为 Asia/Shanghai。
16. 状态分为四个正交维度：识别状态用于截图与草稿流程，平台交易状态用于已付款、已取消、已退款或未知，履约状态用于 `unknown`（未知）、`pending_shipment`（待发货）、`shipped`（已发货）、`delivered`（已收货）或 `returned`（已退货），生命周期状态用于正常、回收站或永久删除。待确认不得混入正式订单交易状态。OCR 仍只产生 `unknown`、`pending_shipment` 或 `shipped` 三种基础识别值，`delivered` 与 `returned` 是人工维护的订单当前值。
16A. 运单号去除首尾空白后非空是唯一有效发货依据，只填快递公司不表示已发货。每次单笔或批量保存时，系统先将每笔订单当前值与补丁合并，再执行基础状态一致性规则：最终为 `pending_shipment` 且有有效运单号时归一为 `shipped`；最终为 `shipped` 且无有效运单号时归一为 `pending_shipment`。即使本次补丁显式指定了这两种基础状态，也必须满足该一致性规则。
16B. `unknown`、`delivered` 和 `returned` 不被手工物流修改静默覆盖。自动联动引起的履约状态变化与同次物流变化必须在一个事务中原子保存，只递增一次订单版本并产生同一条最小修改记录；不得改写 OCR 识别原文、来源快照或已冻结的发货快照。
16C. 来源快照的 OCR 识别值仅使用基础三态；快照的人工确认值可保留 `delivered` 或 `returned`，不得为了适配 OCR 枚举而降级为 `shipped`。
17. 删除订单采用软删除并进入 30 天回收站；永久清理是独立、需二次确认的操作。

### OCR 与入库流程

18. 当前 OCR 适配器调用阿里云百炼中国北京地域的 qwen3.5-ocr。图片可使用 API 支持的 Base64 Data URL 输入，不依赖公共图床。
19. API Key、Workspace ID 与地域在设置页配置。API Key 存入 macOS 钥匙串或 Windows 凭据管理器，不进入数据库、日志、错误报告、导出、备份或代码仓库。
20. 单批最多 50 张，一张图对应一个订单草稿。每张图拥有独立状态，单张失败不回滚同批其他订单。
21. 识别流程覆盖等待识别、识别中、校验中、待确认、已入库、等待重试、失败和重复跳过。断网或可重试服务错误保留任务并按受控退避重试，应用重启后可恢复。
22. 自动入库默认关闭，由用户主动开启。关闭时成功识别的草稿全部进入校对；开启时仍必须通过关键字段完整性、格式、业务一致性和重复检测。
23. 自动入库所需关键字段为订单编号、收件人、手机号、完整地址、至少一个商品明细和成交金额。订单级必填自定义字段没有默认值时，也阻止自动入库。
24. 可疑判断来自确定性规则和多字段交叉检查，不依赖模型自报的字段置信度。可选候选裁决只能从本机给出的候选标识中选择或返回无法确定，不能直接生成订单字段。
25. 每张订单截图正常流程只调用一次百炼 `advanced_recognition` 生成识别原文，本机据此划分六区、隔离推广内容并确定性恢复字段。生产流程不调用 `key_information_extraction`，也不在定位失败时回退生成式结构化提取；定位缺失、关键字段无识别原文依据或截图不完整时建立待确认项。仅当本机规则形成至少两个有限候选且用户已启用候选裁决时，同一截图才最多追加一次独立文本模型调用。
26. 候选裁决采用独立 OpenAI 兼容配置，默认关闭，至少支持 DeepSeek，并可配置百炼或自定义兼容服务。验证 API Key 与 OCR API Key 分开保存在系统凭据库；模型只接收有界 OCR 文字、坐标和候选，不接收截图。识别原文、结构化裁决记录、规范化结果、校对修改和最终入库值应可关联追溯；服务商原始响应不持久化，识别原文也不得包含在普通导出中。
27. 费用统计按实际付费调用计算，包括 OCR 识别、手动重试以及实际发生的候选裁决；本机六区划分和字段规则不计为云端调用。达到月度额度时默认只提醒；只有用户明确启用硬限制时，系统才在下一次付费调用前暂停队列。

### 重复与更新

28. 同一订单编号且规范化内容等价时自动跳过，并记录重复来源，不创建第二笔原始订单。
29. 同一订单编号但字段变化时保留新的来源快照，生成新旧对比并等待确认，不静默覆盖。确认更新后写入字段级审计记录。
29A. 已入库订单允许从详情页编辑当前订单字段和商品明细；保存前展示变化摘要，保存后写入字段级审计记录。普通编辑不改写平台、卖家账号和平台订单编号；只有明确进入“更正订单身份”后才能修改这些字段，并必须重新执行唯一性与重复冲突检查。任何编辑都不改写识别原文、不可变来源快照或已冻结的发货快照。
30. 完全相同的截图可在 OCR 调用前通过内容指纹跳过，以减少费用；订单唯一性仍是最终防线。

### 商品与数量

31. 一个原始订单包含一个或多个商品明细。商品条目未出现明确数量时数量为 1，并标记为系统推定值。
32. 商品明细始终保留截图原始标题和规格；标准商品、标准规格和 SKU 是可选的标准化关联。
32A. 商品明细对管理与导出公开订单号、原始商品标题、原始款式或规格、商品单价、数量、数量来源和商品小计。新数据的数量来源分为人工修改、OCR 识别和系统默认 1；历史数据中能够确定为系统推定的仍标记系统默认 1，其余无法可靠区分人工或 OCR 的标记为已明确但历史来源不明。
32B. 商品数量的当前值按人工修改、OCR 识别、系统默认 1 的优先级选择。人工新增或修改数量后形成显式人工覆盖，之后的 OCR 识别或系统默认值不得静默替换该值；历史来源不明不伪装成人工覆盖。
33. 只有规范化文本完全一致或已有商品映射时才自动归并。模糊相似结果只提供候选，用户确认后才能形成映射。
34. 校对行为只在本机生成映射建议，不自动修改历史订单，也不把校对内容发送给第三方用于训练。
35. 商品目录 Excel 导入必须先预览列映射、候选更新、重复 SKU 和错误行，再由用户确认。

### 买家与合并发货

36. 规范化手机号只用于提示可能来自同一买家的订单，不建立永久买家主档。手机号缺失时，相似姓名或地址只能形成建议。
37. 自动合并发货要求订单处于正常生命周期、平台交易未取消或退款、履约状态为待发货，且规范化手机号和完整地址均一致。地址只做 Unicode、空白和常见标点规范化后的精确比较，不做模糊自动合并。
38. 合并发货组不拥有或覆盖原始订单；它引用成员订单并计算商品、数量、金额和订单数汇总。每笔待发货订单最多属于一个开放发货组。
39. 用户可以手动拆分或重新组合未发货组。跨地址手动合并时必须显式选择最终收货信息，否则不能标记发货或导出发货表；人工操作记录原因和审计事件。
40. 未发货组是动态投影。组被标记已发货时生成不可静默修改的发货快照；后续原始订单变化产生警告。
41. 已取消和已退款订单默认不参与自动合并。已发货组之后出现的同买家订单进入新的未发货组。

### 表格、模板与导出

42. 内置字段库按订单、商品明细和发货组三种数据粒度定义。用户自定义字段必须声明所属数据粒度，可新增文本、数字或金额、日期时间、单选、多选和勾选字段。
43. 每个表格模板必须声明一种数据粒度，并保存字段选择、显示名、顺序、筛选和排序。不同模板读取同一份订单事实；导出脱敏是每次导出的临时选择，不属于模板。
44. 自定义字段可配置默认值与是否必填，并参与对应数据粒度的筛选和排序。第一版不支持用户编写任意公式。
45. 系统提供商品总数量、订单总额、合并订单数和合并总额等受控计算字段。
46. 普通订单导出默认生成订单总表，并可选附加订单商品明细表；从发货组发起导出时固定生成订单总表、订单商品明细表和合并发货表。订单总表一笔订单一行，订单商品明细表一个商品条目一行，合并发货表一个开放发货组一行；每个工作表应用对应粒度的模板。
46A. 订单模板以一个不可拆分的动态商品列组替代商品摘要。系统按当前订单结果或本次所选导出订单中的最大商品条目数，依原商品明细顺序完整展开商品、款式或规格和数量列；商品较少的订单在后续列组留空，不限制业务列组数，也不截断或合并商品。
46B. 动态商品列组在系统订单总表、导出预览和 Excel 订单总表中使用同一投影规则。未来存在标准商品映射时优先显示标准商品名和标准款式或规格，否则回退到截图原文。
47. 导出仅处理用户选择的记录或当前筛选结果；导出前显示记录数、三种模板和脱敏摘要。
48. 系统界面显示完整信息。每次导出默认脱敏：收件人保留姓氏，手机号保留前 3 后 4 位，地址保留省市区并遮盖街道门牌，昵称保留首尾字符；用户可以仅为本次导出明确关闭。未脱敏原文不得残留在隐藏列、批注、元数据或未展示的附加工作表中。
49. 历史订单 Excel 导入必须提供字段映射、预览、错误行下载和确认步骤。平台、卖家账号和订单编号是入库身份必填项；缺失行留在错误预览，不生成伪订单号。没有来源截图的历史订单仍可保存，但标明来源类型。

### 图片、备份与更新

50. 来源截图默认保留。超过 90 天后转换为可核对文字的高质量压缩图，压缩成功并校验可读后才替换原文件；用户也可单独删除某张来源截图。
51. 默认不自动删除截图。用户可选择 180 天或 365 天清理策略；清理前展示预计释放空间并二次确认，结构化订单不随图片删除。
52. 每日增量去重备份覆盖数据库、模板、商品映射和截图，目标保留最近 30 个版本并允许选择目标目录。
53. 备份默认容量上限 5 GB 且可调整。容量上限优先于版本数量，超过上限时从最旧可删除版本开始清理；最近一次完整可恢复备份优先级最高，若它本身超过上限则允许临时超额并明确提示。
54. 恢复前验证备份完整性并保护当前数据；恢复失败不得破坏恢复前状态。
55. 更新采用用户确认的半自动流程。更新前创建并验证备份；程序文件与数据分离，失败时旧版本仍可启动。

### 视觉与交互

56. 界面基调为简洁、清晰、直观、专注和偏商务。表格信息密度优先，闲鱼黄仅作为少量强调色，不照搬闲鱼 App。
57. 空数据状态以截图上传为主要行动；有数据后以订单表为主要界面，并保留全局批量上传入口。
58. 校对界面同时呈现截图、结构化字段、异常原因和修改动作，避免用户在多个页面来回核对。

### 分阶段交付

59. 第一阶段交付核心可用版：双平台免安装启动、数据目录、持久化离线队列、批量截图识别、校对与自动入库、原始订单、来源快照、商品明细、已入库订单编辑、自定义表头模板、带默认脱敏的 Excel 导出、重复保护和最小修改记录。
60. 第二阶段交付业务增强版：合并发货、状态与手工物流、商品与 SKU 映射、商品目录导入和历史订单 Excel 导入。
61. 第三阶段交付稳定完善版：手机局域网上传、备份与容量管理、截图清理、高级模板脱敏配置、完整审计历史界面、回收站、费用统计和应用更新。

## Testing Decisions

1. 主测试缝采用用户已确认的完整订单工作流：给系统一个识别批次和可控 OCR 结果，只验证用户可观察的最终行为，不断言内部函数调用或数据库实现。
2. 主工作流测试覆盖上传、识别、校验、自动入库或待确认、重复处理、商品明细、合并发货投影和 Excel 输出。除 OCR 外尽可能从同一个高层入口驱动。
3. OCR 适配器在测试中使用可控替身，以便覆盖成功、超时、限流、格式错误、区域歧义和识别原文不完整，而不产生云端费用。
4. 阿里云适配器另设最小契约测试，使用脱敏后的固定响应验证请求构造与响应解析；真实付费调用只作为显式手动冒烟测试，不进入默认测试套件或 CI。
5. 业务测试只断言外部结果：订单是否入库、为何被拦截、哪些记录被合并、导出内容为何值、备份能否恢复。不要为 ORM、队列实现、组件内部状态或私有方法编写脆弱测试。
6. 重复测试至少覆盖相同图片、不同图片但相同订单、相同订单字段变化、识别错误导致的候选冲突和跨批次重复。
6A. 已入库订单编辑测试至少覆盖订单字段和多商品明细修改、保存前变化摘要、取消不写入、保存后重启仍存在、字段级审计记录，以及来源快照和已冻结发货快照保持不变。
7. 合并测试至少覆盖同手机号同地址、同手机号不同地址、缺手机号、已取消、已退款、已发货冻结、发货后新订单和人工拆分或重组；跨地址手动合并没有明确选择最终收货信息时不得发货或导出。
8. 商品测试至少覆盖多商品、数量缺失默认为 1、明确数量、完全一致标题、已有映射、相似但未确认标题和重复 SKU 导入。
8A. 数量来源测试至少覆盖人工修改、OCR 明确识别、系统默认 1 和历史来源不明四种展示；同时验证人工修改优先于后续 OCR 或默认值，历史非推定数据不得被猜测为人工或 OCR。
9. 导出测试以真实工作簿读取器重新打开文件：第一阶段验证订单总表和商品明细表，第二阶段起再验证合并发货表；同时验证各自模板、行粒度、列顺序、字段改名和脱敏结果，而不是只验证文件存在。订单号、交易号和手机号必须是文本单元格，金额必须是数值，时间必须是日期时间；未脱敏原文不能藏在隐藏列、批注或其他工作表。
9A. 多商品导出测试至少包含商品条目数不同的多笔订单，验证订单总表动态列组按本次范围完整展开、短订单尾列为空、三个基础表头改名后自动编号，以及商品明细表仍保持一个商品条目一行并导出数量来源。
10. 历史 Excel 导入测试覆盖表头映射、身份必填缺失、重复订单、错误行、无截图来源和确认前不写入；缺少平台、卖家账号或订单编号时不得生成伪订单。
11. 状态测试分别覆盖识别状态、平台交易状态、五种履约状态和生命周期状态，确保待确认不会被当作正式订单状态，取消或退款也不会自动改变历史发货快照。基础履约联动至少覆盖待发货填入运单号转已发货、已发货清空运单号退回待发货、只填快递公司不转换、同次显式基础状态仍被一致性规则归一、未知/已收货/已退货不被覆盖，以及联动与物流同事务、单版本、最小修改记录且来源和冻结快照不变。
12. 数据生命周期测试覆盖 90 天压缩、压缩校验失败不替换原图、可选清理、30 天回收站、备份去重、5 GB 上限、最新完整备份临时超额和恢复失败回滚。
13. 安全测试验证 API Key 不出现在数据库、日志、错误报告、备份、导出文件或版本控制中；手机上传未提供有效临时码时不能访问，且手机页面不能浏览订单。
14. 批次边界测试验证 1 张与 50 张可提交，51 张被明确阻止，多个批次之间的状态和结果互不覆盖。
15. 便携版在当前支持的 macOS 与 Windows 环境分别执行启动、选择数据目录、导入一单、退出重启和读取原数据的冒烟测试。
16. 视觉端到端测试只覆盖高价值路径：空状态上传、批次进度、校对确认、订单筛选、合并组发货和导出。样式细节使用人工视觉验收，不大量依赖像素快照。
17. 第一阶段开始时使用约 10 张真实截图建立开发样本；正式验收使用至少 30 张版式和场景不同的真实闲鱼订单详情截图。
18. 验收标准是订单号、手机号和成交金额必须正确识别或被系统拦截，不能静默入错；其他目标字段按金标中可见且应识别的原子字段计算，准确率至少 95%；多商品条目数必须正确或被拦截；重复订单不得重复入库。
19. 真实截图、识别响应和验收结果存放在不进入代码仓库的私有测试数据目录中。公开或提交的固定样例必须先彻底脱敏。
20. 当前为绿地项目，没有可复用的既有测试先例；实现应优先建立上述单一高层工作流测试缝，再补外部适配器契约与少量跨平台冒烟测试。

## Out of Scope

1. 闲鱼账号登录、页面抓取、非官方接口或自动拉取订单。
2. 自动点击闲鱼“去发货”、自动联系买家、发送消息或修改平台订单。
3. 物流平台 API、电子面单购买、自动查询物流轨迹或承运商结算。
4. 第一版识别淘宝、拼多多、抖音等其他平台；仅预留平台与卖家账号扩展能力。
5. 识别订单列表、聊天记录、物流页或其他非订单详情页面。
6. 一个订单跨多张截图自动拼接，或一张截图包含多个订单的自动切分。
7. 多用户账号、团队协作、角色权限、审计责任人体系、公共 SaaS、订阅和计费。
8. Mac 与 Windows 的云端实时同步、多人同时编辑或冲突合并。
9. 任意自定义公式、完整电子表格计算引擎或宏。
10. 依据模糊标题自动静默合并商品。
11. 用用户校对数据训练或微调第三方模型。
12. 库存、采购、会计总账、发票、税务和利润核算。
13. 桌面端启动密码或默认界面脱敏。
14. 第一阶段提供经过商业证书签名和公证的安装包；内部便携版可能仍触发操作系统的首次安全提示。
15. 默认自动永久删除来源截图或订单数据。
16. 默认测试或持续集成中执行真实付费 OCR 请求。
17. 手机端查看、搜索、编辑或导出订单；首版手机页面只负责上传。
18. 修改历史的任意版本一键回滚；第一版只保证来源证据与修改记录可查看。

## Further Notes

1. 当前模型与服务为阿里云百炼 qwen3.5-ocr，中国北京地域。官方 API 参考：https://help.aliyun.com/zh/model-studio/qwen-vl-ocr-api-reference
2. 开发启动前由用户先提供约 10 张真实订单详情截图，随后补足至少 30 张验收样本；样本应包含长截图、多商品、不同金额、重复买家、重复订单和不同订单状态。
3. 真实截图包含姓名、手机号和地址，只能保存在本机私有数据或用户自己的阿里云调用链路中，不得提交到 GitHub。
4. 技术选型应服从本规格的运行契约：Mac 与 Windows 免安装、本机数据目录、可靠后台任务、系统凭据存储、局域网手机上传和可测试的 OCR 适配器。具体 UI 框架与桌面壳在实施计划中确定，不属于产品行为。
5. 规格涵盖三阶段最终产品。任务拆分必须保持阶段边界，正式发布仍必须在第一阶段验收通过后进入第二阶段。当真实样本不足时，可以按 ADR 0008 先行开发后续功能，但不得宣告前一阶段已通过、复用旧发布证据或放宽其验收门槛。
