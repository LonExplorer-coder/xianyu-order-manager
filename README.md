# 闲鱼订单管理系统

一个面向个人卖家的本机订单管理工具：批量识别包含闲鱼订单详情的来源截图，将结果校对后汇总为可自定义表头的订单表、商品明细表和合并发货表。

当前版本 0.2.65 已完成发货与售后、预售与团购履约计划、库存与采购、财务与经营结果四个业务闭环的自动化验收，并已提供商品目录工作簿交换与历史导入。应用从来源截图识别、校对或历史工作簿开始，能够持续管理原始订单、发货组档案、包裹、售后处理、库存流水、采购订单、待确认资金事项、资金记录与已实现利润，并在关闭重开、备份恢复及 Mac/Windows 免安装版读回时保持历史一致。

项目尚未宣告正式发布：真实订单样本暂不足，发布候选仍须在同一提交上完成完整 CI、至少 30 张私有金标截图验收和双平台产物证据。同一 Wi-Fi 手机上传、来源截图容量治理、模板级导出脱敏、OCR 费用控制和便携版更新仍由后续 Issue 推进。

## 当前可运行能力

- 首次启动选择独立数据目录，之后自动打开最近目录；正常运行时可在设置页查看当前路径并安全切换到已有目录或新的空目录。
- 空数据状态突出批量上传入口；已有订单时仍以订单表为主，并保留最近识别批次摘要。
- 有订单时首页显示在库订单、全部待确认和待发货数量；订单工作台支持全局搜索、买家与商品独立搜索、日期区间、平台、卖家账号、来源识别状态、平台交易状态、履约状态和生命周期状态的组合筛选与排序。
- 正常订单可移入 30 天回收站，期间不进入正常工作台、履约计划和开放发货组；用户可恢复订单，也可经二次确认永久删除。30 天到期由系统自动处理，商品、来源证据、发货档案与快照不被静默改写，所有生命周期操作均保留不可变事件。
- 字段库可创建订单级、订单商品明细级或合并发货组级的文本、数字、金额、日期时间、单选、多选和勾选字段；字段可设默认值与必填，并与内置业务事实分开保存。
- 自定义值与平台订单事实分开保存，可在新订单校对、订单更新校对和订单详情中填写。人工确认与详情保存会拦截最终状态中缺失的必填值；订单级必填字段没有默认值时，自动入库会转为人工确认。
- 订单工作台可切换“订单 / 商品”视图，并按对应粒度的自定义字段筛选与排序；多选字段按“包含全部所选项”筛选，勾选字段提供“未设置 / 是 / 否”三态，金额精确保存到分，日期时间固定按 Asia/Shanghai 显示。
- 可保存多套订单、订单商品明细或合并发货表格模板，每套独立保存字段选择、表头别名、列顺序、筛选和排序；可使用商品总数量、订单总额、合并订单数和合并总额等受控计算字段，不提供任意公式入口。
- 应用模板时会原子恢复对应粒度、列与查询；可显式回到默认视图，删除正在使用的模板也会同步恢复默认结果，不会留下隐藏筛选。
- 标准商品页可维护唯一 SKU、标准商品名和标准规格。订单校对时，标题与规格完全一致或已有商品映射才自动关联；相似文字只显示候选，人工确认后可选择是否记住这组订单原文。订单原始标题和规格始终保留，也不会因为后来建立映射而批量改写历史订单。
- 标准商品页可导入或导出商品目录工作簿。导入先选择“标准商品”和“商品映射”的工作表及列映射，再逐行预览候选新增、候选更新、重复 SKU 与错误；重复 SKU 必须明确选择保留行，商品映射必须明确提供适用范围，标题别名改指向另一标准商品时还须填写变更原因。确认前不会写入，错误行不会阻止其他有效行确认，目录在预览后发生变化则必须重新预览。导出只包含标准商品和当前有效商品映射，并保留映射的适用范围、平台与卖家账号；每张表最多 10,000 条、整个工作簿最多 10 MB，所有成功导出的文件均可直接重新导入。
- 订单工作台可导入历史订单 Excel 工作簿。工作表与列对应先自动建议且可人工修正，然后预览新增、字段级更新、重复和错误；平台、卖家账号或平台订单编号缺失时不伪造临时身份。同一订单的多行合成多件商品，单笔最多 100 个商品行；错误行可下载为新工作簿，且在确认前不写入。更新时保留未映射的可选列，并复用既有订单的重复、版本、数量优先级、自定义字段、商品标识、商品标准化与履约事实保护；导入来源保存文件名和原行号，不伪造来源截图或识别事实。
- 收件人管理按姓名和规范化手机号建档，提供永久收件人编号、可读订单编号、回购单、收件人累计消费和累计退款投影；归类错误通过带原因的收件人合并修正，不覆盖原始订单历史。
- 预售与团购可建立履约计划：预售订单立即形成有效预售需求并支持分批采购建议，团购在人工确认成团后把条件性需求转为确定需求；订单只有在明确释放后才进入开放发货组。
- 库存页按可销售、待检查、瑕疵品和报废四态展示库存流水，并单列已预留数量与可用现货。采购到货、原始发货、售后补发、退货检查、拦截退回和未交寄撤销均通过来源事实记账，重复业务事实不会重复产生流水。
- 采购页可维护供应方、采购建议、采购订单、分次到货和供应方退货；采购订单确认后形成采购在途数量与采购应付事项，退款或需求重算不会静默改写已经确认的采购事实。
- 资金页把待确认资金事项与资金记录分开保存：售后实际退款和承运索赔同意只自动立待确认事项，人工确认后才形成不可变资金记录；部分确认、取消剩余和冲正均保留历史，业务状态变化不会自动制造资金事实。
- 利润页按订单展示成交金额参照、平台结算、退款、服务费、运费、承运理赔、采购成本、待确认净额和已实现利润，并可按标准商品汇总下钻。采购成本采用到货和供应方退货形成的加权平均采购单价，待确认资金不混入已实现利润。
- 普通订单导出默认生成“订单总表”，可选附加“订单商品明细表”；从开放发货组导出时固定生成“订单总表”、“订单商品明细表”和“合并发货表”，三张表分别选择对应粒度模板并可逐表预览。
- 导出只在生成文件时默认遮盖收件人、手机号、详细地址和买家昵称，不修改系统内原始数据；订单号、交易号、手机号、金额和时间分别按适合 Excel 再处理的文本、数值与日期类型保存。
- 订单表直接展示平台与卖家账号、完整收件人/手机号/地址、多商品摘要和四个互不混用的状态维度；打开详情可继续核对完整订单、来源截图和历史变化。
- 可从订单表或详情单笔维护，也可勾选最多 200 笔订单批量维护平台交易状态。履约状态是由有效发货记录、包裹商品数量和包裹物流计算的只读投影，共有未知、待发货、部分发货、已发货和已收货五种；快递公司与运单号在对应包裹中维护，不能从订单上直接覆盖。
- 确认实际发出、部分发货、包裹签收、发货记录作废或补发时，系统从业务事实同步重算履约状态并追加发货同步修改记录，不改写 OCR 来源快照或发货快照。已取消或已退款订单仍可查询，但不会进入待发货结果或计数；平台交易状态不参与履约计算。
- 发货组页面按手机号与完整地址精确匹配待发货订单，展示成员订单、商品汇总、数量和金额；缺少手机号或地址的订单单独提示补全。
- 可从多成员开放发货组中拆出指定订单，也可勾选多个开放组重新组合。跨不同发货匹配键时必须从成员订单中选择最终收货信息；手工调整保留原因和不可变记录，不修改原始订单。
- 可从开放发货组选择全部或部分商品数量，精确分配到一个或多个包裹后确认实际发出；系统生成可追溯的发货记录和快照，剩余数量继续开放。未实际交寄的误操作包裹可带原因撤销，物流信息可留痕更正，原订单后续变化只显示差异提醒。
- 发货页面按待发货、部分发货和已全部发货组织工作；同一轮分批产生的多条发货记录归入唯一发货组档案，档案卡展示收货信息、关联订单、商品数量和发货情况，再向下展开包裹明细。已全部发货只表示本轮待发数量归零，不代表已收货或售后结束；相同收货信息以后的新订单不会混入既有档案。
- 每个有效包裹只维护待承运方接收、运输中、已签收或已退回四种正常物流状态；拦截、丢件、破损、错投等改为独立物流异常事实，可与正常运输、买家侧售后、退款或补发、承运索赔并行。状态更新及承运方、运单号更正均保留修改前后值、原因和时间，且不改写发货快照或订单履约状态。
- 订单详情把跨流程信息统一投影为“当前待办 → 未解决风险 → 并列事实 → 折叠完整历史”；当前待办只突出一项，其余待办显示数量并可展开，可直接定位到所属发货记录或售后处理单。交付时限、资金风险、实物风险和普通跟进依次排序；终态后的晚到事实仍可补录，但不会重新打开已结束流程。
- 可从发货记录选择具体发货快照商品与数量建立售后处理单，并维护处理中、等待退回、等待检查、等待退款、等待补发、部分完成和已完成七种进度。每次状态、问题原因和商品数量变化都会留下不可变处理时间线；多个未完成售后不能静默占用超过已发数量，已完成历史不能重新打开，物流与售后互不改写。
- 仅退款保留申请金额与实际退款金额，不生成退货记录；退货退款依次记录退货物流、实际收到、检查结果和实际退款。取消待确认退款后，已发生的退货仍可继续记录收到与检查，不会复活退款、改写原发货或猜测库存。
- 退货包裹可保留物流信息更正史、合装商品及订单归属，并独立处理丢件、破损、错投等异常和承运索赔；买家退款、退货实物与承运赔付互不改写，售后结案后仍可记录承运结果或找回包裹。
- 售后流程页内置仅退款、退货退款、换货、直接补发、拦截退回、丢件处理和其他处理七套只读预置。预置可停用或复制；自定义流程可调整有限步骤、必需或可选、字段要求和一层显示条件，不提供循环或任意脚本入口。
- 新建售后必须选择已启用的售后流程，处理单冻结当时的流程版本并显示已完成、当前与后续步骤。中途调整场景只追加新的流程选择和后续处理轮次，已有退款、退货、补发、异常与索赔事实不会被覆盖。
- 旧版零散发货记录升级后，成员订单有交集的历史档案及其后续普通履约发货档案会自动归并，完整保留各次发货记录和包裹，总件数则按唯一订单商品去重计算；只在收货信息相同而订单不同的情况下继续分开。
- 单批可选择 1–50 张截图，51 张会被明确阻止；可连续创建多个批次，每张图独立显示等待识别、识别中、校验中、待确认、已入库、等待重试、失败、重复跳过或已取消。
- 选中的截图会先复制到数据目录的本机队列；离开批次页或退出应用都不会丢失未完成任务，重启后会从持久化状态继续处理。
- 断网或云服务暂时不可用时，单张截图按 30 秒、2 分钟、10 分钟、30 分钟、30 分钟受控退避，最多自动重试 5 次；同批其他截图不受阻塞。
- 等待重试或失败的单张任务可“立即重试”，也可“人工录入”生成空白校对草稿；两种操作都只影响目标截图，并保留来源图与最终来源快照。
- 把来源截图以 Base64 Data URL 直接发送到用户自己的中国北京百炼 `qwen3.5-ocr`，不依赖公共图床。
- 每张截图正常只调用 1 次 OCR：完整图通过 `advanced_recognition` 生成识别原文（含文字、坐标及原始响应），本机按六个订单区域用确定性规则拆分字段并隔离推广内容。不会再让 OCR 模型生成省市区等派生字段；定位缺失、规则歧义或截图不完整时转入人工确认。
- 自动入库默认关闭；可在设置页立即开启或关闭。关闭时所有识别草稿先校对，开启后仅有完整、格式有效且无冲突的订单直接进入原始订单表。
- 自动入库不使用模型自报置信度；系统确定性校验订单号、收件人、手机号、完整地址、商品、金额、时间和商品明细合计。平台优惠可能使成交金额不等于商品总价加运费，因此不会把这种差额直接判为冲突；坐标定位失败、识别原文缺失、规则歧义或截图不完整都会进入待确认。
- 批次页和校对页会显示结构化的待确认原因；这些原因随订单草稿保存，重启后仍可继续核对。
- 完全相同的图片会在付费 OCR 前按内容指纹跳过；内容指纹会在请求发出前持久保存，即使识别失败或应用重启，相同副本也不会重复发起付费调用，需从原失败项执行重试或人工录入。不同图片识别为同平台、同卖家账号、同订单号且内容等价时，只追加不可变来源，不创建第二笔订单。
- 同一订单的新截图若包含字段变化，无论自动入库是否开启都会保存为待确认来源；校对页明确展示当前值与新识别值，只有点击“确认更新订单”才会更新当前值。若 OCR 误把新订单命中已有订单，可直接修正卖家账号或订单号，系统会重新判断为新订单或切换到正确的已有订单。
- 每次确认更新都会校验订单版本并记录最小字段变化；过期校对会刷新当前版本并保留尚未提交的人工修正，不会覆盖较新的确认结果。订单详情可切换查看历次来源截图、对应修改版本和字段前后值。
- 识别订单号、支付宝交易号、买家与收货信息、地址、下单/付款时间、商品总价、运费、成交金额及一个或多个商品明细；通过页面位置约束区分买家昵称和收件人，并在模型漏拆时从完整地址补拆省、市、区县。
- OCR 未识别到的金额保留为空白并阻止确认；用户明确填写 `0.00` 才按零元保存。
- 识别 `×N`、`xN`、`数量 N`、`共 N 件` 等明确数量；截图未显示数量时默认记为 1，并在校对页直观提示“截图未显示数量，已按 1 件处理”。
- 对照来源截图校对规范化结果后确认入库；识别原文、规范化结果和最终值分开保留。
- 可取消本次校对：不会生成订单，且该草稿之后不能误入库；来源截图与识别原文仍保留以便追溯和后续容量清理。
- 订单、商品明细、来源截图及不可变来源快照保存在本机。
- 关闭并重开后继续查看原始订单；同一数据目录只允许一个写实例。
- 在设置页配置中国北京地域的百炼 `qwen3.5-ocr`，API Key 只保存到 macOS 钥匙串或 Windows 凭据管理器。
- 手动测试 OCR 连接；必须在费用提示中再次确认，默认测试和 CI 不发起付费调用。

## 本地开发

需要 Node.js 24.18.x 和 pnpm 10。项目根目录的 `.node-version` 已固定当前验证版本。

```bash
pnpm install
pnpm start
```

常用验证命令：

```bash
pnpm check
pnpm package
```

两平台免安装 ZIP 在对应系统上构建并验证：

```bash
# Apple 芯片 Mac
pnpm make:mac:portable
pnpm verify:portable

# 64 位 Windows
pnpm make:windows:portable
pnpm verify:portable
```

验证会从最终 ZIP 启动程序两次：首次选择独立数据目录并建立订单、发货、售后、履约计划、库存、采购、资金和利润历史，删除第一份程序目录后，再从第二份程序读回同一数据目录并核对关键金额与历史；同时检查最终 ZIP 中的来源截图和系统凭据库。日常 CI 会保留 ZIP、SHA-256 和机器可读验收证据 14 天。

macOS 普通本地打包会对整个应用执行临时签名，因此钥匙串功能可用；这个包仅适合本机或内部验证。正式对外分发使用 Apple Developer Program 的 `Developer ID Application` 证书，并把公证凭据保存在 macOS 钥匙串，而不是项目文件中：

```bash
xcrun notarytool store-credentials xianyu-order-manager-notary \
  --apple-id "你的 Apple ID" \
  --team-id "你的 Team ID"
pnpm make:mac:release
pnpm verify:mac:release
```

`notarytool` 会安全提示输入 Apple ID 的 App 专用密码。正式构建会自动启用 Hardened Runtime、Developer ID 签名和 Apple 公证；验证命令会检查签名、公证票据及 Gatekeeper。若要使用其他钥匙串配置名称，可通过 `XIANYU_NOTARY_KEYCHAIN_PROFILE` 指定。

Electron 只通过受限 preload 接口向界面开放目录选择、订单操作和不可读取原文的 OCR 凭据操作。结构化数据使用 Node 内置 SQLite，来源截图保存在所选数据目录的 `screenshots` 子目录；程序目录可以独立替换。

如需人工验证自己的百炼配置，请在“设置 → 百炼 OCR”中保存 Workspace ID 和 API Key，再点击“测试连接”。第二次确认后，应用会把一张程序内置的合成图片直接发送到百炼，这可能产生一次 OCR 调用；订单截图不会参与该连接测试。之后每张订单截图正常产生 1 次真实 OCR 调用：完整图生成识别原文，本机定位平台状态、收货、商品、金额、订单详情和履约操作六区，再从相应区域的识别原文确定性恢复订单字段。定位缺失、规则无法唯一判断或截图不完整时，识别原文仍会保留，结果进入人工确认，不再追加结构化 KIE 复核。

真实识别验收建议一次选择 2 张尚未入库、包含完整订单详情的截图：确认批次页会逐张更新且离开该页后仍继续处理，再分别核对订单号、交易号、买家昵称与收件人是否分离、手机号、省市区、三种金额、多商品条目数、明确数量和时间。修改任一字段并确认入库后，关闭并重开应用，订单详情应继续显示最终值和来源截图。

队列恢复验收可在正在识别或等待重试时退出应用，移动或删除原上传位置的文件后重开：历史批次应仍在，任务应使用数据目录内的队列副本继续。若服务持续失败，可确认“立即重试”仅重试该行；“人工录入”应打开带原图的空白校对页，填写后入库仍会产生不可变来源快照。取消流程可另上传一张合成或废弃截图验证：点击“取消本次校对”后应回到批次页，且不会新增订单。

自动入库验收可先保持默认关闭，上传一张完整截图并确认它进入待校对；再在“设置 → 自动入库”中开启开关，分别上传一张完整订单和一张缺少订单号或手机号的截图。前者应直接出现在订单表，后者应停在待确认并显示具体原因。关闭并重开应用后，开关状态和待确认原因应继续保留。

重复与更新验收可先确认一张订单，再重复上传完全相同的图片：批次结果应提示未再次调用 OCR。随后上传同一订单的另一张等价截图，应提示已记录新来源且订单表仍只有一笔。若新截图中的收件人、金额、状态或商品明细发生变化，校对页应显示当前值与新识别值；取消不会改变订单，确认后订单版本递增、详情保留两份来源，并可查看本次实际变化的字段。

订单工作台验收可准备多笔不同日期、买家、商品和状态的订单：确认首页三项数量准确、最近批次和上传入口可见；分别使用全局搜索、买家、商品、日期、平台/卖家和四种状态组合筛选，再切换金额或时间排序。表格应显示完整收件信息和多商品摘要，进入详情再返回后筛选条件仍保留；没有匹配结果时可直接清除筛选。

自定义字段验收可在“字段库”分别创建订单级文本字段、订单商品明细级勾选字段和合并发货组级拣货区域字段。前两种字段设置默认值后，应确认既有订单与新订单均获得该值；再创建一个无默认值的订单级必填字段，开启自动入库并上传新订单，确认它停在人工校对。补齐订单及每件商品的必填字段后入库，在详情修改并保存，重开应用确认值仍在；最后在订单、订单商品明细和发货组工作台分别应用包含自定义字段筛选或排序的模板。发货组字段应从开放发货组行内编辑，重开后仍保留；组级必填值缺失时应阻止发货组三表导出。

表格模板验收可先在订单工作台设置“待发货 + 金额倒序”，再在“表格模板”创建订单模板，选择内置字段、一个订单自定义字段和受控计算字段，修改表头并调整顺序后保存。应用后应同时恢复筛选、排序、列名与列顺序；切换“默认视图”应恢复默认结果。再分别创建订单商品明细模板和合并发货模板，确认三套模板不会混入其他数据粒度的自定义字段。合并发货模板应能选择成员订单、商品汇总、合并订单数、商品总数量、合并总额及组级自定义字段，并恢复组级筛选和排序。关闭重开应用后三套模板都应保留。

标准商品验收可先在“标准商品”创建 SKU、标准商品名和标准规格，再上传标题与规格完全一致的订单，确认校对页自动关联且订单原文仍在。随后上传一张只有相似标题的订单，确认系统只显示候选、不预先选中；人工选择候选并勾选“记住这组订单原文”后入库，再上传同样原文的新订单，应按已有映射自动关联。最后修改标准商品名称，确认订单当前展示同步更新，但原始标题、原始规格和过去订单的关联身份没有被重写。

商品目录工作簿验收可先在“标准商品”页导出当前目录，确认文件含“标准商品”和“商品映射”两张表；复制一个 SKU 行、修改一条商品名并新增一条合法商品，再把一条标题别名的 SKU 改为另一已有 SKU 后导入。列映射应按导出表头自动选中，预览应分别显示重复 SKU、标准商品和商品映射的候选更新及候选新增；选择重复 SKU 的保留行前不能确认，标题别名候选更新未填写原因时也不能确认。完成选择和原因后可确认其他有效行，错误行继续留在预览且不写入。再次导出并导入新的空数据目录，SKU、标准商品名、标准规格及当前有效商品映射的原始标题、原始规格、适用范围、平台和卖家账号应保持一致。

历史导入验收可准备一份含平台、卖家账号、平台订单编号、收货信息、金额和商品明细的 `.xlsx` 文件：用两行表示同一订单的两件商品，再加一行缺少平台订单编号的错误数据。选择文件后应自动建议列对应，预览显示一笔多商品新增和一行错误；下载错误行应保留原表头、原行号和错误原因。确认后只建立合法订单，详情显示来源文件和原行号而不显示来源截图。再次导入相同文件应只跳过重复；只映射必填列更新时，应保留原有的交易号、时间、状态和商品规格。修改同一订单的收件人或商品后应先显示字段级前后值，确认才递增订单版本并追加来源与订单修改记录；已有商品自定义字段、人工数量或发货事实时，导入不得让这些已确认信息丢失或回退。

Excel 导出验收可先筛选出数笔订单，直接点击“导出当前结果”；再勾选其中一笔，确认按钮和预览切换为“导出已选”。普通订单导出默认只生成订单总表，勾选后才附加订单商品明细表。随后进入发货组，选择一组或使用当前组结果导出，分别为三张表选择模板并逐表查看预览；保存后重新打开工作簿，订单总表应一单一行，订单商品明细表应一条商品明细一行，合并发货表应一组一行并包含成员订单和商品汇总。默认脱敏时，收件人只保留姓氏、手机号只保留前 3 后 4 位、地址只保留省市区、买家昵称只保留首尾字符；仅为本次导出关闭脱敏后预览和文件才显示完整值，系统内原始信息始终不变。收件信息仍有歧义且未确认最终值的发货组不得导出。

平台交易与履约验收可在订单表勾选两笔订单，批量把平台交易状态改为已取消或已退款，确认订单仍能按对应状态查询，但不会进入待发货结果；弹窗不应提供履约状态、快递公司或运单号编辑。另准备一笔多商品订单，先只确认部分商品发出，再发出剩余商品并把有效包裹更新为已签收，确认履约状态依次投影为部分发货、已发货和已收货；每次变化都应留下发货同步修改记录，来源截图和发货快照保持不变。

财务闭环验收可准备一笔成交 100 元的订单，分别登记平台结算 98 元、首发运费 8 元和补发运费 8 元，再建立部分退款、采购付款、供应方退款、三类退货检查结果以及丢件赔付待确认事项。资金页应只把人工确认的金额列入资金记录，利润页应把未确认退款和赔付单列；关闭重开、备份恢复以及便携版写入/读回后，资金记录、待确认余额、采购成本和已实现利润应保持一致。

## 隐私说明

上传订单截图后，完整图片会发送到用户所配置的阿里云百炼服务执行一次 `advanced_recognition`，生成识别原文；本机随后划分六个订单区域、隔离推广内容并用确定性规则恢复字段。规则只采用相应区域的识别原文，省、市、区县只从完整地址拆分；无法可靠确定时留空并要求人工确认，不会回退到生成式结构化提取。单张原文件上限为 7.5 MB，网络请求禁止自动重定向。原图、结构化订单和不可修改的识别原文同时保存在用户选择的本机数据目录。API Key 仅由系统凭据库保存，不进入订单数据库、日志、识别原文、备份或导出；若上游异常回显实际密钥，应用会拒绝保存该响应。真实来源截图、API Key、本机数据库和备份不得提交到代码仓库；自动化测试只使用程序生成的脱敏合成图片与固定服务端响应，不发起付费调用。
